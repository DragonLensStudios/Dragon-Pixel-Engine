# ADR-0014: Project Components and Worker-Only Runtime Modules

> **Status:** Proposed
> **Date:** 2026-07-25
> **Design revision:** `DPE-ARCH-0012`

## Context

Dragon Pixel already stores language-neutral component records and exposes hard-coded native/managed descriptors, but the production editor cannot discover a project component manifest. The only C# generator is isolated in POC C, no C++ registration generator exists, and workers do not load project assemblies or native component modules. The sample managed Rotator is interpreted by a hard-coded type switch; it is not evidence that arbitrary project C# code executes.

The editor must feel component-oriented without putting untrusted or incompatible game code in the Qt process. A missing build output must not make its authoring data disappear or become destructive.

## Decision

- Project format version 3 declares contained `componentRoots`. Metadata format version 4 describes component category/policy, implementation language, contained source path, optional runtime module identity, stable type/schema identity, and the existing ordered property descriptors.
- The editor metadata service reads and validates only JSON manifests. It rejects unsafe paths, duplicate IDs, invalid defaults, unsupported schema versions, and owner/language mismatch before replacing its active registry. It never loads a project assembly or native library.
- **Create C# Script** and **Create C++ Component** are bounded source-generation workflows. They create contained source stubs and matching metadata entries with new UUID type identity through atomic writes. A generated but unbuilt component remains addable/serializable and is explicitly diagnosed as runtime unavailable.
- **Build Components** is an explicit out-of-process operation. It writes only contained generated/build/cache outputs, emits platform/architecture/build-hash module manifests, reports structured diagnostics, and restarts workers after success. It never compiles on each Inspector edit.
- Production C# builds use `DragonPixel.Contracts` attributes and a source generator to emit deterministic metadata plus worker-side factory registration. C++ builds use explicit declarations/code generation to emit the same metadata plus a worker-only, size-tagged `dpe_component_plugin_v2` C function table. Workers retain exact `dpe_component_plugin_v1` fallback compatibility for existing pre-v2 project modules.
- A build-generated runtime-module manifest binds module UUID/build hash/platform/architecture to its component type IDs and entry point. Preview/play workers validate and load it; the editor passes the manifest but never maps its code.
- Managed factories and native C ABI plugins instantiate by stable entity and component type IDs. Managed `IProjectComponent` keeps its existing `Initialize`/`Update`/`Shutdown` compatibility surface; the optional `IProjectComponentLifecycle` extension supplies enable, fixed, late, render-submission, and disable stages. Native v2 supplies the equivalent stages through a lifecycle-phase dispatch callback.
- `IGameObjectControllerLifecycle` and the abstract `GameObjectController` provide the recommended concise C# authoring layer over those existing worker interfaces. Controllers expose a stable entity `Guid`, protected input/time access, and one shared worker-owned `Transform` with `System.Numerics.Vector3` position/Euler-rotation/scale values. Existing direct interface implementations remain compatible.
- A worker constructs one managed transform per entity from the immutable snapshot. Controller writes mark only runtime state dirty; after component and physics updates, dirty managed transforms override the disposable render/pick scene for that frame. Reload/Stop/crash discards them, and no write reaches the editor-owned authoring scene. Managed-on-physics transform writes are final render/pick overrides until an explicit engine-owned physics-control contract exists.
- Dispatch order is create/initialize, enable, bounded 60 Hz fixed updates, variable update, late update, render submission, disable, and destroy/shutdown. At most four fixed catch-up calls run per presented update; excess time is dropped with a diagnostic. A stage failure disables only that instance and performs best-effort disable/destroy cleanup.
- Add Component exposes New C# Script and New C++ Component entry points. After contained generation and metadata activation, the new stable component type is attached to the selected GameObjects through one validated transaction. It remains authorable but runtime-unavailable until the explicit Build Components operation succeeds.
- Project Explorer indexes stable contained C#/C++ source/header files below declared component roots. Inspector component cards and source-row activation delegate editing to a bounded `ScriptEditorService`; neither surface opens or interprets source itself.
- The script-editor service regenerates a disposable Rider solution/project beneath `.dragonpixel/Ide/Rider`, includes every validated component source, and uses an argument-vector detached process launch to open the solution and selected file. Rider configuration/discovery and launch failures produce diagnostics and never make source execution part of the editor process.
- Lifecycle failures become structured diagnostics. Native exceptions and managed exceptions are contained within their respective worker boundaries.
- Worker restart is the reload mechanism. Stop/crash destroys every component instance and runtime-only transform. No project component can write the editor-owned scene directly.
- Missing, stale, incompatible, or failed modules leave records visible and losslessly preserved. Runtime activation is disabled for that type, and the diagnostic names the required module/build.

## Consequences

The editor remains stable and can inspect a project without executing it. Build tooling and workers gain generators, registrars, version negotiation, module resolution, and lifecycle complexity. Source creation can arrive before arbitrary runtime loading as long as the UI labels unbuilt components honestly and acceptance does not claim execution support.

DPE-ARCH-0009 connects project components to declared project-v4 build targets. Each target selects its adapter, configuration, platform, architecture, toolchain/SDK, and required runtime modules; builds execute only in supervised workers and return hash-bound structured results. Runtime module references in cache and packages use normalized relative paths contained beneath approved roots and bind module UUID, component type IDs, platform/architecture, ABI/capabilities, build/input hashes, and artifact hash. The editor never maps build or package outputs, and workers reject path/reparse/symlink escapes, stale or mismatched hashes, and undeclared modules.

DPE-ARCH-0010 makes the already-designed common lifespan explicit and backward compatible. Existing managed components and native v1 modules retain their established three-stage behavior. New generated components use the managed lifecycle extension or native v2 table, while module manifests continue to bind stable type/module identity independently of implementation language or ABI generation.

DPE-ARCH-0011 makes source editing an explicit external-tool boundary. Indexed component sources remain project-owned inputs, the Rider workspace is disposable derived state, and editing never implies build, reload, lifecycle execution, or authoritative scene mutation. Stable type identity remains metadata-owned rather than filename- or solution-owned.

DPE-ARCH-0012 makes the recommended managed authoring API smaller without replacing its compatibility transport. Generated C# scripts derive from `GameObjectController` and override parameterless `Enabled`, `Disabled`, `Update`, and `FixedUpdate` methods. The base class alone maps those methods onto the full existing worker lifecycle and exposes immutable input plus disposable transform state. Inspector omits lifecycle as a fake property and continues to show only source identity and serialized fields.

## Alternatives considered

- **Reflect/load project code in the editor:** rejected because it violates crash, security, compatibility, and AOT boundaries.
- **Treat source filenames or qualified names as identity:** rejected because renames would corrupt durable references.
- **Use a C++ class ABI across plugins:** rejected because compiler/STL/runtime combinations are not a stable cross-platform boundary.
- **Hide records when code is missing:** rejected because it risks data loss and makes repair impossible.
- **Compile on every Inspector edit:** deferred; build orchestration, dependency restore, and arbitrary code execution need separate UX/security work.
- **Embed a code editor or Rider protocol client:** rejected for 1.0 because Dragon Pixel is not a general-purpose IDE; a contained external process launch provides the authoring handoff without expanding the editor's trust boundary.

## Validation and acceptance gate

POC I must prove metadata-v4/project-v3 validation and deterministic migration, C# and C++ golden parity, contained source indexing, deterministic disposable Rider-workspace regeneration, safe launch routing, Inspector/Project edit actions, editor-process exclusion, worker-only factory/plugin loading, ordered create/enable/fixed/variable/late/render/disable/destroy dispatch, bounded catch-up/drop behavior, legacy managed/native-v1 compatibility, stage-specific error containment, restart cleanup, and missing-module preservation on Windows, macOS, and Linux. Until that evidence is reviewed, this ADR remains `Proposed`, custom source creation/editing is an authoring preview, and arbitrary project C#/C++ execution is not called supported.

DPE-ARCH-0012 additionally requires base-class dispatch, stable GUID binding, per-entity transform sharing, input/time propagation, generated mover property parsing, actual render/pick displacement, runtime-state discard, legacy compatibility, and Inspector omission evidence on every baseline platform. Native transform-control parity remains open and must not be represented by passing managed objects across the C ABI.

DPE-ARCH-0009 extends POC I and adds POC R coverage for declared target selection, clean worker builds, worker-only module loading, package relocation, contained path resolution and hash validation, missing/tampered/extra/wrong-platform rejection, rebuild/restart, and clean-install execution on every baseline. KNI packaging remains governed by ADR-0004. No POC R or complete three-platform evidence is accepted yet, so the earlier POC I gate and `Proposed` status remain unchanged.

Current Windows evidence (2026-07-25): project-v3/component-metadata-v4 manifests are validated without loading binaries. Generation is constrained to declared component roots; projects with multiple roots require an explicit selected root. The build identity now includes the exact `dotnet` binary and `--info`, CMake binary/version, C++ compiler identity, generator, and pinned build-program/Ninja identity. Nested generated projects use the repository's CMake 3.25 floor, and inputs are re-enumerated after the build so a mid-build metadata change cannot be silently published. Explicit builds produce build-hash/platform/architecture cache placement and runtime manifests with contracts, generator, tool, source, and artifact identities.

Worker-only validation requires the exact version-1 manifest shape, canonical UUID-v4 identity sets, declared source roots, platform/architecture/Release/generator/contracts/tool matches, build-hash-derived placement, contained regular no-link files, and pre/post artifact SHA-256 equality. Managed assemblies load from verified bytes; native modules are leased and rechecked before load. Factory/plugin publication is atomic, missing enabled non-builtin factories are diagnosed, managed `Shutdown` runs after an `Initialize` exception, native handles are destroyed after property failures, and component input dictionaries are immutable copies. Hostile tests cover tampering, deletion, links, placement, build hash, platform/architecture, IDs, factories, native identity, initialization failures, and input mutation.

Current Windows DPE-ARCH-0010 evidence (2026-07-26): both registered runtime aliases pass in Release (0.20/0.19 seconds) and MSVC AddressSanitizer (0.51/0.48 seconds), covering ordered managed/native v2 lifecycle dispatch, native v1 fallback, bounded four-step fixed catch-up/drop, initialization/property/stage failure containment, and disable-before-destroy cleanup. Both component generator aliases pass in Release (25.48/23.98 seconds) and AddressSanitizer (26.62/24.28 seconds), including managed lifecycle/native-v2 source surfaces, isolated builds, and cache integrity. The complete Qt interaction alias passes in Release (84.73 seconds) and AddressSanitizer (111.73 seconds), including direct generated-script attachment to the selected GameObject without editor-process project-code loading. The earlier complete 45/45 Windows matrices remain historical baseline evidence; an unrelated intermittent atomic-publication recovery defect must be resolved before a new authoritative full-matrix claim. Current Ubuntu/macOS generation, build-cache, managed/native worker loading, crash/restart, and adapter-host conformance runs remain outstanding.

Current Windows DPE-ARCH-0011 evidence (2026-07-26): project-index/model coverage proves stable source/header/metadata entries and the Scripts / Components filter; service coverage proves deterministic Rider solution/project regeneration, source/manifest item inclusion, explicit discovery precedence, missing/outside/link rejection, and exact solution plus `--line` launch arguments without opening Rider. Qt coverage proves immediate post-generation visibility plus Project Explorer and Inspector edit actions. The five focused aliases pass Release in 83.89 seconds and MSVC AddressSanitizer in 104.67 seconds. The local Rider installation is discoverable, but automated evidence injects a launcher and does not take ownership of the external IDE. This remains one-platform partial POC I evidence.

Current Windows DPE-ARCH-0012 evidence (2026-07-26): contract/runtime tests prove stable GUID binding, concise enable/fixed/update/disable dispatch, immutable input and timing, a shared `Vector3` transform, delta-scaled movement, render-scene overlay, and reset/discard while retaining the existing direct-interface managed and native-v1/v2 paths. Generator tests compile the new controller-based mover in isolated project builds, and Qt automation proves the Inspector omits Lifecycle while retaining Script Source and editable Speed. Release runtime aliases pass in 0.20/0.20 seconds, generator aliases in 23.31/20.21 seconds, and the registered interaction alias in 83.13 seconds. All five matching MSVC AddressSanitizer aliases pass in 143.15 seconds. The exact writable `MyMover` builds without warnings/errors, the refreshed 157-file developer bundle hash-verifies, and its MonoGame self-test exits zero. The first bundle refresh exposed a locked Rider workspace and was repaired by preserving the writable sample and updating engine/runtime payloads in place by default; `-ResetSample` is now the only destructive sample reset. No new actual-device managed-controller pixel/pick, Stop/crash lifecycle, native transform, cross-platform, or release-package evidence is claimed.

Open production risks include path-based TOCTOU and hard-link/native-loader races, in-place rebuild of an invalid cache directory, publication/read races, absolute developer paths and package relocation, a synchronous editor build UI, native ABI full-state parity, and complete metadata default/shape/range/step plus generated-identifier validation. Production dependency resolution and a language-symmetric serializer/source-generator golden suite also remain part of POC I/POC R. This ADR therefore remains `Proposed`.
